## Context

`大翻译数据处理` 现在已经具备真实 AI provider 接入，但一次真实业务测试暴露出新的系统短板：任务失败后，系统只保留了“第几行失败”和一个总括性错误消息，却没有保留足以判断根因的运行事实。对于 429、timeout、5xx、配置错误和无效响应，目前界面几乎给出同一张脸。

这说明系统已经越过“脚本能不能跑”的阶段，进入了“产品能不能被维护”的阶段。运行日志不只是给开发者看的调试附件，它会成为后续自动重试、节流、模型 fallback 和生产排障的事实底座。

## Goals / Non-Goals

**Goals:**
- 为任务运行建立结构化事件流，而不是只保留最终状态。
- 为 AI 调用保留足够诊断字段，使失败原因可以被区分和复盘。
- 让用户在工作台中看到最近一次任务的关键运行过程，而不必翻本地文件。
- 为后续恢复策略提供可机读的数据基础。

**Non-Goals:**
- 不在本 change 中直接实现完整的限流调度、自动重试策略或模型降级。
- 不建设外部日志平台、日志搜索中心或长期归档系统。
- 不把底层敏感信息原样暴露到前端。
- 不要求首版 UI 展示每一个底层字段；先保证数据被正确捕获。

## Decisions

### 1. 以 task-local structured events 作为第一版日志形态

每个 task / attempt 继续作为本地持久化主对象，在其中新增结构化 `events` / `diagnostics` 字段，而不是立刻引入独立日志服务。

**Why:** 当前产品仍处于第一条真实流程阶段，任务本身就是最自然的排障上下文。把日志先贴着任务存，能最快形成可用反馈回路。

**Alternative considered:** 立即接入独立日志平台。长期方向合理，但会过早把一条可观测性 change 扩成基础设施项目。

### 2. 区分“用户可见摘要”和“诊断细节”

前端默认展示人能读懂的摘要：失败阶段、失败类别、最近成功到哪一行、是否建议重试；更细的 HTTP 状态、provider code、request ID、耗时等仍保留在任务详情中，但不暴露密钥和原始提示词。

**Why:** 好日志不等于把机器内部全倒给人看。首要目标是让用户能判断发生了什么，让开发者能继续钻下去。

**Alternative considered:** 只在服务端写详细日志，前端继续只显示失败文案。这样开发者可查，但用户仍然失明。

### 3. AI 调用诊断必须能区分失败类别

共享 AI 层要把至少以下情况分开：`rate_limited`、`timeout`、`provider_error`、`configuration_error`、`invalid_response`。如果 provider 返回 request ID、HTTP status 或业务 code，也应随 trace 一并保留。

**Why:** 后续恢复策略完全依赖这个分辨率：429 才值得降级，timeout 更适合重试，配置错误则应该停止重试。

**Alternative considered:** 继续统一归类为 `ai_provider_unavailable`。实现最省事，但会阻断后续一切更聪明的恢复动作。

### 4. 事件流围绕阶段边界记录，而不是围绕每一行泛滥打印

任务日志至少记录：创建、校验通过、attempt 开始、工作表开始、AI 调用开始/结束/失败、attempt 完成/失败。逐行调用保留摘要字段，但不把正文原文和密钥写入日志。

**Why:** 这样既能复盘，又不会把日志变成另一个庞杂数据副本。

**Alternative considered:** 每一步都打印完整 payload。调试爽，但很快会制造噪音和安全风险。

## Risks / Trade-offs

- **[日志字段过多导致前端难读]** → 区分摘要层与诊断层，默认先展示高信号字段。
- **[记录不足仍无法排障]** → 以这次真实失败为回归样本，确保 timeout / HTTP status / provider code / request ID 可见。
- **[日志泄露敏感内容]** → 明确禁止持久化 API key 和原始 secret，必要时对 provider response 做白名单提取。
- **[未来迁移到数据库后结构再次变化]** → 先固化语义，再在生产化 change 中迁移存储。
