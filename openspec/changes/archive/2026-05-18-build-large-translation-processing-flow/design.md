## Context

`大翻译数据处理` 目前已经有三层基础：

1. 用户需求已经被证明稳定：上传原始 Excel，系统批量生成中文一句话摘要与分类，再交付结果文件。
2. 主规格已经描述了该工作流的核心行为，包括文件接收、AI 摘要、分类规则、产物归档和失败重试。
3. v1 工作台壳层已经完成，但仍停留在占位状态，尚未形成真实生产闭环。

这次 change 先把前端工作台、任务接口、Python 处理和文件产物真正接起来，形成第一条可运行垂直切片。此前已经确定的正式架构方向——Next.js Web 层、Python 文档处理服务、PostgreSQL/Prisma、Redis-backed Celery worker、S3-compatible object storage——仍然保持不变，但生产级运行时接入将由后续 change 单独完成，避免把“业务闭环验证”和“基础设施生产化”揉成一个过重改动。

## Goals / Non-Goals

**Goals:**
- 让用户在 `大翻译数据处理` 工作台中完成“上传 → 启动 → 查看状态 → 下载结果”的完整闭环。
- 将 Excel 校验、摘要生成、分类、结果写回和产物归档串成一条真实任务链路。
- 让失败可见、可解释、可重试，而不是让用户面对黑盒。
- 为后续日报类自动化工作流沉淀一套可复用的任务、AI、产物和重试边界。

**Non-Goals:**
- 不在本 change 中建设通用工作流编辑器、模板编辑器或列映射配置 UI。
- 不扩展到日报候选池、日报正文生成或本地同步。
- 不在第一版开放批量多文件上传、手动调整分类词表或任意模型切换。
- 不把大翻译流程过度泛化成“所有 Excel 都能处理”的平台能力。
- 不在本 change 中完成 PostgreSQL / Prisma、Redis-backed Celery、MinIO / S3 适配和部署级基础设施。

## Decisions

### 1. 采用异步任务语义，而不是在上传请求中同步完成处理

上传成功后先创建任务，再由 worker seam 执行处理。当前 change 在本地使用轻量任务存储与进程内调度，前端通过任务查询轮询显示状态；正式队列化运行时将在后续 change 中替换为 Celery。

**Why:** Excel 解析、逐行摘要、写回和归档都会随数据量增长而变慢；同步请求会让用户等待、让失败边界模糊，也不利于后续重试与审计。

**Alternative considered:** 单请求直出结果。实现更快，但会把第一条正式生产链路做成一次性脚本式行为，后续无法自然复用。

### 2. 维持“固定业务契约”，不在首版暴露列映射或模型参数

系统按已知的大翻译模板识别输入结构，校验必要列位，并把输出写回既定字段。

**Why:** 用户最想摆脱的正是机械配置；当前规则已被历史工作验证稳定，首版应优先承接稳定动作，而不是把内部实现重新抛回给人。

**Alternative considered:** 让用户在 UI 中选择 sheet、来源列、摘要列和分类列。灵活，但会把旧劳动换一种方式重新放回界面。

### 3. 将处理链路拆成可测试的四段

1. workbook audit / validation  
2. AI summary generation  
3. deterministic classification  
4. workbook write-back + artifact archive

**Why:** 这样能把“不合法文件”“AI 失败”“分类规则异常”“写回失败”分层暴露，便于测试、重试和后续复用。

**Alternative considered:** 一个大函数从读取到导出一口气完成。开发初期更快，但一旦失败，用户和系统都很难知道哪里坏了。

### 4. 分类优先采用稳定规则，再处理兜底分类

诸如 `台湾问题`、`欠薪讨薪相关` 等高优先级规则先执行，避免被模型表达波动覆盖；只有在无高优先级规则命中时，才进入既定 taxonomy 的兜底分配。

**Why:** 分类是该流程中最“制度化”的部分，稳定性比创造性更重要。

### 5. 每次任务运行都保留原始输入、结果产物和可审计上下文

任务至少记录：原始上传文件、模板/工作流标识、任务状态、失败摘要、处理统计、输出文件、AI 生成关联。当前 change 先通过本地文件持久化验证这些对象边界；后续生产化 change 再迁移到正式数据库和对象存储。

**Why:** 这既支撑下载、排错和重试，也让第一条自动化链路从一开始就具备可追溯性。

### 6. 重试在同一任务下创建新的执行尝试，而不是要求用户重新上传

如果失败属于可恢复问题，用户应能基于同一输入重试；系统保留历史尝试和新产物版本。

**Why:** 这符合用户心智，也与 artifact versioning 保持一致。

## Risks / Trade-offs

- **[输入模板存在历史变体]** → 首版先支持当前已确认的模板结构；对不匹配的文件给出可理解的拒绝原因，而不是静默失败。
- **[AI 输出可能不稳定]** → 通过固定提示词、结果校验和 deterministic classification 降低波动；对 AI 异常显式失败并支持重试。
- **[大文件处理耗时较长]** → 使用异步 worker 和任务状态展示，避免阻塞前端请求。
- **[过早泛化会拖慢首条链路落地]** → 坚持只实现大翻译已知契约，不提前建设通用 Excel 配置平台。
- **[本地垂直切片与正式架构存在差距]** → 将当前实现限制为边界清晰的本地适配层，并另起生产化 change 处理 Prisma、Celery 与 S3/MinIO。
- **[首个端到端任务会暴露数据模型不足]** → 以该流程为最小真实样本完善 task / artifact / attempt 结构，后续再抽象共性。
