## Context

大翻译数据处理当前已经具备三层基础能力：真实百炼 provider、结构化运行日志、以及行级并发。现状的问题不是“不能跑”，而是“跑得太慢”：即便 6 并发已经接入，只要每一行仍然触发一次远程调用，165 行文件依然需要大量请求，延迟波动也会被累加。

这个 change 的目标不是引入复杂编排系统，而是在现有 worker 架构内，把执行单元从“单行”提升为“批次”，同时保留三件事情：可追踪、可恢复、可配置。

## Goals / Non-Goals

**Goals:**
- 让大翻译数据处理默认按批次调用 AI，而不是逐行调用。
- 允许批次并发执行，并通过环境变量控制批大小与最大并发。
- 当批次失败或批量输出不可解析时，自动降级为单行处理，从而尽量完成任务。
- 保留足够的日志，能说明哪个批次成功、失败或发生降级。

**Non-Goals:**
- 不改动前端工作台的整体交互结构。
- 不引入外部队列、中间件或新的持久化层。
- 不实现跨任务的调度器或全局限流器。
- 不在这次 change 中改造国际日报或其他工作台。

## Decisions

### 1. 使用“批量摘要 + 本地分类”的混合执行模型
- **Decision:** AI 仅负责批量生成中文摘要；分类继续沿用本地规则函数。
- **Why:** 分类规则稳定、廉价且可预测，不值得让模型重复承担；这样批量调用的 token 更集中于真正需要 AI 的摘要任务。
- **Alternative considered:** 让模型同时返回摘要与分类。被拒绝，因为会加大 prompt 复杂度并削弱现有稳定分类规则。

### 2. 在共享 AI 层新增批量摘要接口
- **Decision:** 在 `services/worker/shared/ai.py` 中新增批量摘要能力，由 worker 以列表方式提交输入并拿回顺序对齐的摘要数组。
- **Why:** 批量能力属于 AI 层通用能力，不应只长在单个 workflow 里。
- **Alternative considered:** 在 worker 中自己拼 prompt 和解析响应。被拒绝，因为会把 provider 细节再次泄漏回 workflow 层。

### 3. 默认采用“批量并发 + 批失败降级到单行”
- **Decision:** worker 先按 `XIAOYU_AI_BATCH_SIZE` 切批，再按 `XIAOYU_AI_MAX_CONCURRENCY` 并发执行；若批调用失败或返回无效结果，且 `XIAOYU_AI_BATCH_FALLBACK_ENABLED=true`，则将失败批次拆成单行继续处理。
- **Why:** 这是兼顾吞吐与稳定性的中间路线。整份文件一把调用虽然更激进，但一旦结果损坏会让恢复变得非常困难。
- **Alternative considered:** 整份文件一次调用。被拒绝，因为不可控、不可局部恢复、也更容易超时或产生超长输出。

### 4. 日志以“批次为主，行为辅”
- **Decision:** 运行日志新增批次事件；批量成功时记录行区间与批次耗时，降级时记录失败批次与回退动作。
- **Why:** 用户最关心的是“跑到哪一段卡住了”，不是每一行都刷一条日志。
- **Alternative considered:** 继续只记行级日志。被拒绝，因为批处理后会失真，也不利于解释性能。

## Risks / Trade-offs

- **[批量响应格式不稳定]** → 使用严格的 JSON 输出约束，并在解析失败时自动降级到单行处理。
- **[并发过高引发上游波动]** → 保持并发可配置，默认先与当前 6 并发对齐。
- **[批量成功但个别摘要质量下降]** → 先保持摘要任务简单，若后续出现明显质量回退，再为失败批次引入更细粒度补偿。
- **[日志模型变化影响现有 UI 认知]** → 保留失败摘要兼容逻辑，并扩展事件文案而不是重写日志区。

## Migration Plan

1. 新增批量配置变量到 `.env.example` 与运行时文档。
2. 在共享 AI 层实现批量摘要接口与批量 trace 结构。
3. 在 translation worker 中切换为批处理调度，并加入失败降级路径。
4. 更新日志格式化与测试。
5. 使用 stub/provider mock 跑通批量成功与批量降级两条回归路径。
