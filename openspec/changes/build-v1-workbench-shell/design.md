## Context

小舆的第一版目标是先把人从重复、机械的旧流程中解放出来，而不是先堆叠复杂业务能力。当前系统已有三类首批工作流的主规格，其中“大翻译数据处理”属于文件处理型流程；“国际日报”和“国际热点日报二处”已被重新明确为共享日报引擎下的两种日报生产型流程。

因此，首个 UI change 不应再把全部工作台统一建模为“上传文件后开始处理”，而应建立统一入口下的两类工作台骨架，为后续真实能力接入预留正确的结构。

## Goals / Non-Goals

**Goals:**
- 让用户在进入系统后的前 30 秒内清晰找到当前要处理的工作台。
- 为文件处理型与日报生产型工作流分别建立符合其真实任务模型的 v1 页面骨架。
- 为三个首批工作流提供一致但不过度同质化的基础体验。
- 建立后续可复用的导航、布局、状态和结果呈现模式。

**Non-Goals:**
- 不实现联网搜索、候选池生成、AI 成稿、文档导出、本地同步或真实批处理逻辑。
- 不实现复杂权限、模板编辑器、自由工作流编排或历史任务管理。
- 不在本 change 内完成任何日报候选池数据或真实文件处理结果的生产。

## Decisions

- 采用“工作台式”首页，而非向导式或流程编排式入口；首页首屏直接展示三个业务工作台卡片。
- 首页使用业务名称作为主标题，并用一句副标题解释结果，例如“大翻译数据处理 / 批量生成中文摘要与分类”。
- 建立两类工作台骨架，而不是单一万能骨架：
  - 文件处理型：输入区、处理状态区、结果区。
  - 日报生产型：候选池区、已选篮子、草稿区、导出区。
- `大翻译数据处理` 在 shell 阶段即展示真实的上传心智：用户看到一个明确的原始 Excel 上传入口。
- `国际日报` 与 `国际热点日报二处` 在 shell 阶段不展示选题文件上传区，而是展示未来会承接真实数据的候选池与已选篮子结构。
- 首版只暴露业务动作，不暴露底层参数；例如不要求用户手动选择列位、模型、模板版本或搜索策略。
- 对尚未接入的能力使用清晰的占位状态与说明，而不是伪造完整业务流。

## Risks / Trade-offs

- 两类工作台骨架会让首个 UI change 比“全量统一壳层”略复杂，但能显著减少后续日报功能接入时的返工。
- 在尚未有真实候选池数据时先展示日报骨架，页面会存在部分占位内容；这比错误地引导用户上传选题文件更符合长期产品形状。
- 过早引入完整日报交互会超出本 change 的边界，因此这里只固定信息架构和区域结构，不提前实现复杂行为。
